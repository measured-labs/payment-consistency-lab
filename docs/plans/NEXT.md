## 다음 작업 후보 (우선순위순)

### N1. ADR-001 정합성 판정 · 관측 하네스 — 우선순위: 높음 · 이후 모든 ADR의 판정 도구

- **왜 다음인가**: ADR-000 §9 — "우리 DB와 PG가 일치하는가"를 셀 도구가 없다. 이번 스모크의 비교는 curl + psql 수작업이었다.
- **발생 가능한 문제(관측 신호)**: ① 응답 유실 1.0에서 PG에만 승인이 남았다(DB 0행) — 정합성 검증기는 PG 쪽 사실을 꺼낼 길이 필요하다(mock PG 원장은 메모리 · 재기동 시 사라짐 · 내보내기 없음) ② 장애 주입이 시드 없는 무작위라 같은 실패를 다시 만들 수 없다 — 판정 결과를 재현하려면 결정적 주입이 필요해질 것이다.
- **방법론 선택지**: mock PG 원장 내보내기(관리 API) vs 주문번호별 조회 반복(지금 API만) — 규모가 커지면 조회 반복은 비용이 크다. 결정은 ADR-001 인터뷰에서.
- **착수 전 확인할 것**: 판정 항목(이중 승인 · PG만 승인 · 금액 불일치 · 취소 누적 불일치 · **우리 DB 안의 `canceled_amount` = 취소 행 합계** — 동시 부분 취소의 갱신 유실은 PG와 비교하기 전에 우리 쪽에서 먼저 드러난다) · 결정적 주입 범위 · 부하 도구(k6) · 서버(.9 · .158).

### N2. Q7 커넥션 풀 고갈 · Q2/Q6 결과 불명 — 우선순위: 중간 · ADR-001 뒤

- **관측 신호**: PG 지연 2초 · 동시 30에서 풀 10개 전부 `idle in transaction` · p50 5.4초. 응답 유실 → 504 + PG만 승인.
- **착수 조건**: ADR-001 정합성 검증기로 수치를 잴 수 있을 때.
- **순서 주의**: 결과 불명 처리가 PG 주문번호 조회에 기대면, 한 주문번호에 결제 행이 여러 개인 Q1 문제(중복 요청 방지)를 먼저 풀어야 조회 결과를 우리 행 하나에 붙일 수 있다. 취소 쪽 결과 불명은 취소 모델 확장(요청 상태)이 필요하다(ADR-000 §9).
- **Q5 정산 대조 전 선행**: 취소 1건 식별자를 PG 응답 · mock PG 기록 · 우리 취소 행에 저장(ADR-000 §9).
